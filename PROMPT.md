## 1. ПОЛНОЕ ОФИЦИАЛЬНОЕ УСЛОВИЕ ЗАДАЧИ (КЕЙС ХАКАТОНА)

### 1.1. Бизнес-контекст и проблематика
Машинное обучение стало критически важным инструментом бизнеса: скоринг, прогнозирование спроса, антифрод, рекомендательные системы. Число таких задач растет быстрее, чем штат квалифицированных ML-инженеров.
Главное узкое место индустрии — не в вызове функции `fit()`/`predict()`, а в **исследовательском поиске решения (AutoResearch)**:
* Для каждой новой задачи инженер вручную разбирается в предметной области и словаре данных;
* Проверяет несколько принципиально разных гипотез и подходов;
* Возвращается к конструированию признаков (Feature Engineering), очистке и схеме валидации;
* Этот цикл занимает дни и недели и практически не переносится между задачами.
Классический AutoML (например, Azure AutoML, TPOT) лишь перебирает фиксированные алгоритмы и гиперпараметры внутри жестко заданного скрипта, но не способен понять физический смысл признаков, проанализировать природу ошибок модели и перестроить стратегию решения. Создаваемый AI-агент должен восполнить этот пробел, действуя как полноценный end-to-end исследователь.

### 1.2. Формальная постановка задачи
Необходимо разработать агентную систему, которая полностью автономно:
1. **Анализирует задачу**: читает текстовое описание (`task.md`), изучает структуру входных таблиц и словарь признаков (`data_dictionary.csv`), определяет тип задачи (регрессия, классификация и т. д.), целевой признак, ID-колонку и целевую метрику.
2. **Готовит данные**: выполняет сжатие типов данных (Downcasting), корректную обработку пропусков, аномалий и категорий без утечек данных (Data Leakage).
3. **Реализует цикл AutoResearch**: выдвигает содержательные доменные гипотезы, пишет и исполняет код генерации признаков, обучает модели, оценивает качество на честной валидации, сравнивает с предыдущими результатами и сохраняет только подтвержденные улучшения.
4. **Формирует портфель решений и ансамбли**: не ограничивается одной моделью, а исследует разнородные семейства алгоритмов и объединяет их.
5. **Обеспечивает абсолютную универсальность**: единый программный код должен решать любые задачи (как представленные на публичном этапе, так и скрытые приватные датасеты) без ручной адаптации.

### 1.3. Данные публичного этапа

Все CSV-файлы используют кодировку UTF-8, запятую в качестве разделителя колонок и точку в качестве десятичного разделителя. Пустая ячейка означает пропуск (`NaN`). В каждой задаче агент получает унифицированный набор файлов:
* `train.csv` — обучающая выборка;
* `test.csv` — тестовая выборка (без целевой переменной);
* `data_dictionary.csv` — метаданные колонок (название `feature`, роль `role`, тип `dtype`, единицы измерения `unit`, описание на русском языке `description_ru`);
* `sample_submission.csv` — шаблон сабмита (`id` + целевая колонка).

#### Задача 1. Определение годового удельного энергопотребления зданий (Регрессия)
* **Цель**: предсказать показатель `site_eui` (Energy Use Intensity, кБТЕ/кв. фут) для здания.
* **Обучающая выборка (`train.csv`)**: 53 308 строк, 64 столбца (62 входных признака, `id`, `site_eui`).
* **Тестовая выборка (`test.csv`)**: 22 449 строк, 63 столбца (`id` и 62 признака).
* **Словарь признаков (`data_dictionary.csv`)**: описывает все 64 колонки (климатические характеристики, параметры здания, классы энергоэффективности).
* **Целевая метрика**: **RMSE (Root Mean Squared Error)**:
  $$\text{RMSE} = \sqrt{\frac{1}{n} \sum_{i=1}^{n} (y_i - \hat{y}_i)^2}$$
  *Минимизируется (чем меньше, тем лучше).*

#### Задача 2. Определение типа кибер-атаки по сетевому трафику (Многоклассовая классификация)
* **Цель**: классифицировать сетевую активность по 10 категориям атаки (`attack_cat`: Normal, Generic, Exploits, Fuzzers, DoS, Reconnaissance, Analysis, Backdoor, Shellcode, Worms).
* **Обучающая выборка (`train.csv`)**: 87 670 строк, 44 столбца (42 входных признака, `id`, `attack_cat`).
* **Тестовая выборка (`test.csv`)**: 41 166 строк, 43 столбца (`id` и 42 признака).
* **Особенность**: экстремальный дисбаланс классов (класс `Worms` составляет менее 0.1% выборки).
* **Целевая метрика**: **Macro F1-score** (среднее гармоническое по всем классам с равными весами):
  $$\text{Macro } F_1 = \frac{1}{K} \sum_{k=1}^{K} F_{1, k}, \quad F_{1, k} = \frac{2 \cdot \text{Precision}_k \cdot \text{Recall}_k}{\text{Precision}_k + \text{Recall}_k}$$
  *Максимизируется (чем выше, тем лучше). Accuracy и Weighted F1 носят справочный характер.*

### 1.4. Скрытые задачи приватного этапа (Private Test)
* На финальном этапе решение автоматически перезапускается платформой на **двух абсолютно новых скрытых датасетах**.
* Содержание, модальность, типы задач (регрессия, бинарная классификация, многоклассовая, временные ряды и т. д.) и целевые метрики скрытых задач заранее не раскрываются.
* Платформа запускает то же самое решение через единую точку входа `solution.py`. Ручная правка кода между публичным и приватным этапами исключена.
* Итоговый результат участника в соревновании рассчитывается на приватных датасетах.

### 1.5. Формула скоринга и расчет лидерборда
Метрика каждой задачи на тестовой выборке нормируется относительно зафиксированного организаторами бейзлайна ($B_{\text{RMSE}} > 0, B_{\text{F1}} < 1$):
* Результат на уровне бейзлайна или хуже дает **0 баллов**;
* Идеальный результат дает **100 баллов**;
* Итоговый Score публичного лидерборда:
  $$\text{Score}_{\text{public}} = \frac{S_1 + S_2}{2} \in [0, 100]$$
* Итоговый Score приватного лидерборда рассчитывается аналогично как среднее арифметическое нормированных баллов по двум приватным задачам.

## 3. СУТЬ И ВЫЖИМКА ИЗ СОЗВОНА С НАСТАВНИКОМ КЕЙСА

### 3.1. Ключевые требования наставника к идеальной системе
1. **Максимальное сжатие данных (Data Compression)**:
   Оптимизация датасета обязательна на 1-м шаге (Downcasting, сжатие разрядности чисел, словарное кодирование). Это кратно ускоряет обработку, экономит RAM и позволяет запускать больше итераций моделей.
2. **Абсолютная универсальность**:
   Система обязана работать с любыми типами данных и самостоятельно определять тип задачи по текстовому промпту/файлу задачи.
3. **Формирование «портфеля решений» (Model Portfolio)**:
   Система не должна зацикливаться на одном алгоритме. Агент должен предлагать и исследовать несколько принципиально разных архитектур моделей.

### 3.2. Типы данных и задач, которые должна распознавать система
* **Типы данных**: табличные данные, временные ряды, текстовые признаки, графовые структуры, потоковые данные, изображения/фотографии.
* **Типы задач**: классификация (бинарная, многоклассовая, многозначная), регрессия, поиск аномалий (outlier/novelty detection), кластеризация, прогнозирование временных рядов, change point detection (точки разладки), ранжирование, рекомендательные системы, детекция и сегментация.

### 3.3. Шесть групп метрик, которые обязан извлекать и отслеживать агент
1. **Структурно-лингвистические метрики промпта**: семантический смысл, роль автора задачи, выявление неявных ограничений.
2. **Метрики постановки задачи**: тип ML-задачи, целевой показатель, бизнес-ограничения, вычислительный бюджет, требования законодательства (152-ФЗ, конфиденциальность).
3. **Метрики данных**: структура, качество разметки, пропуски, типы колонок, распределения, дисбаланс, выбросы, временная структура.
4. **Метрики рисков и безопасности**: защита от data leakage, контроль саботажа и мошенничества.
5. **Метрики самого агента**: confidence (степень уверенности в выборе модели), точность определения задачи, предотвращение «обмана метрик».
6. **MLOps и lifecycle-метрики**: логирование гипотез, версионирование, воспроизводимость, мониторинг ресурсов.

### 3.4. Архитектурные рекомендации и проблемы
* **Мультиагентная архитектура (5–6 ролей)**: разделение обязанностей (роутер/профайлер, аналитик данных, инженер признаков, ML-моделист, валидатор/критик, координатор).
* **Промпт-роутинг**: быстрое определение типа модели и задачи по первым фрагментам контекста без лишних задержек.
* **Авторесерч и «обман метрик»**: агент оптимизирует ровно ту метрику, которую видит. По исследованиям Weco AI, агенты склонны «взламывать метрику» в 63% случаев (переобучение на валидацию, подгонка). Требуется строгая, изолированная и честная проверка гипотез.
* **Гетерогенное ранжирование**: сравнение моделей разной природы с учетом времени их обучения (быстрая простая модель vs тяжелая сложная модель).
* **Иерархические метрики**: валидация от уровня семейства моделей до гиперпараметров конкретной модели.
* **Точка останова (Stopping Criteria)**: четкие критерии прекращения перебора гипотез (бюджет времени, стагнация метрики `patience`) для предотвращения холостых циклов.

## 4. МАТЕРИАЛЫ И СПЕЦИФИКАЦИИ MLOPS (ИЗ `dev_tools/PIPELINE.md`)

### 4.1. Сквозная схема процесса создания модели
```
[Запрос пользователя + описание данных + ограничения]
  ↓
[Формализация ML-задачи и формирование Паспорта эксперимента]
  ↓
[Проверка схемы и первичный профиль данных (EDA)]
  ↓
[Выбор схемы разделения: Train / Validation / Test]
  ↓
[Построение обучаемой предобработки без утечек (Data Leakage Free)]
  ↓
[Генерация быстрого Fail-Safe Baseline (Правило 1-й минуты)]
  ↓
[Пул моделей-кандидатов (Multi-fidelity поиск на малых ресурсах)]
  ↓
[Отсев слабых кандидатов и увеличение вычислительного бюджета]
  ↓
[Итеративный цикл Feature Engineering + Feature Pruning]
  ↓
[Подбор гиперпараметров и ансамблирование (Blending)]
  ↓
[Финальная валидация и генерация релизного артефакта]
```

### 4.2. Паспорт эксперимента (Structured Experiment Passport)
До начала любых тяжелых вычислений агент обязан сформировать структурированный паспорт задачи:
```yaml
task:
  type: regression | classification | anomaly_detection | clustering | time_series
  target: string
  prediction_unit: string
  prediction_time: timestamp | null
  prediction_horizon: string | null
data:
  modality: tabular | multimodal
  entity_id: string
  time_column: string | null
  target_available: boolean
evaluation:
  primary_metric: string
  metric_direction: maximize | minimize
  quality_threshold: float | null
  critical_segments: list
  error_costs: dict | null
resources:
  search_budget_seconds: int
  final_fit_budget_seconds: int
  memory_limit_gb: 32
  cpu_limit: 8
  gpu_allowed: false
sampling:
  confidence_level: 0.95
  acceptable_error: float | null
```

### 4.3. Проверка данных и предотвращение утечек
* **Блокирующие ошибки (Fatal Errors)**: отсутствие целевой колонки в train, невозможность прочитать схему, отсутствие редких классов в разбиении, заглядывание в будущее во времени.
* **Диагностические предупреждения (Warnings)**: пропуски, дисбаланс, высокая кардинальность категорий, ID среди признаков, константные признаки, выбросы.
* **Принцип детерминизма**: вычисление статистик и проверка схемы выполняются детерминированным Python-кодом, а не домыслами LLM.
* **Изоляция выборок**: любые обучаемые трансформации (импутация медианой, скалирование, Target Encoding, PCA) обучаются **строго на Train-части внутри фолда**. Тестовая выборка изолирована.

### 4.4. Специфика валидационных разбиений
* **Случайное разбиение (Random Split)**: только для независимых i.i.d. объектов.
* **Стратифицированное (Stratified Split)**: строго обязательно для классификации с сохранением пропорций классов.
* **Групповое (Group Split)**: если один объект/клиент представлен несколькими записями, и модель должна обобщаться на новые группы.
* **Временное (Time-based Split)**: обучение на прошлом, проверка на будущем. Перемешивание во времени запрещено.

### 4.5. Каталог проверяемых преобразований признаков (Feature Engineering)
Агент может конструировать признаки только через детерминированные операции с паспортизацией каждой формулы:
* Отношения и балансы величин (строго с защитой от нуля: `+ 1e-5`);
* Разности взаимосвязанных показателей (амплитуды, спреды);
* Скорости и интенсивности передачи (`величина / (duration + 1e-3)`);
* Логарифмирование неотрицательных величин `np.log1p(x.clip(lower=0))`;
* Агрегации по группирующим ключам;
* Взаимодействия и парные произведения.
Новый признак принимается только при подтвержденном статистическом улучшении на одинаковых фолдах валидации.

### 4.6. Спецификации по типам задач

| Тип задачи | Baseline | Базовые модели | Градиентный бустинг | Метрики качества |
| :--- | :--- | :--- | :--- | :--- |
| **Регрессия** | Константное среднее / медиана | Ridge, ElasticNet | CatBoost, HistGradientBoosting | RMSE, MAE, $R^2$ |
| **Классификация** | Мажоритарный класс | Logistic Regression, ExtraTrees | CatBoost, HistGradientBoosting | Macro F1, Log Loss, ROC-AUC |
| **Поиск аномалий** | Статистический квантиль | Isolation Forest | One-Class SVM, LOF | AP, Precision@k, Recall@budget |
| **Кластеризация** | Случайное разбиение | K-Means, MiniBatchKMeans | DBSCAN, HDBSCAN | Silhouette Score, Davies-Bouldin |

* **Работа с дисбалансом в классификации**: оптимизация матрицы порогов принятия решений (Threshold Tuning) под редкие классы и взвешивание классов (`class_weight="balanced"`), калибровка вероятностей.
* **Работа со скошенным таргетом в регрессии**: логарифмирование таргета при обучении и физический клиппинг предсказаний в диапазон допустимых значений `[y_min, y_max]`.

### 4.7. Трехконтурная система оценки и Агент-Монитор
* **Контур 1 (Fast Check)**: фиксированная мини-выборка валидации для отсева грубых багов и крашей за секунды.
* **Контур 2 (Confirmation Sample)**: статистически значимая кросс-валидация для подтверждения гипотез.
* **Контур 3 (Final Test Audit)**: независимая проверка финального пайплайна.
* **Система статусов Агента-Монитора**:
  * `PASS` — гипотеза статистически улучшила метрику, состояние принимается;
  * `FAIL` — ухудшение метрики или переобучение, активируется **Rollback** к предыдущему лучшему состоянию;
  * `UNCERTAIN` — изменение в пределах шума ($\Delta \approx 0$), не принимается;
  * `NEEDS_REVIEW` — требуется экспертная оценка.
* **Метрика эффективности инфраструктуры (TTQ — Time-to-Quality)**: минимизация времени достижения заданного порога качества.

## 5. МАТЕРИАЛЫ MLOPS ПО СЖАТИЮ ДАННЫХ И ПРОМПТ-РОУТИНГУ (ИЗ `dev_tools/...ipynb`)

### 5.1. Каталог методов сжатия и оптимизации данных
1. **Числовые типы (Downcasting)**:
   * Проверка фактических `min`/`max` и понижение разрядности: `int64 -> int32/int16/int8`, `float64 -> float32/float16`.
   * Использование беззнаковых типов (`uint8/uint16/uint32`) для счетчиков и флагов.
2. **Категориальные данные**:
   * Приведение редких категорий в категорию `"Other"`.
   * Словарное кодирование (Dictionary encoding / LabelEncoder) с минимальным потреблением памяти.
3. **Семантическая очистка (Feature Pruning)**:
   * Удаление константных и квазиконстантных признаков (`nunique <= 1`).
   * Удаление дублирующихся колонок.
   * Экспресс-оценка важности признаков (`feature_importance == 0.0`) и отсечение мусорных колонок для снижения переобучения.
4. **Форматы и память**:
   * Использование эффективных бинарных структур в памяти, предотвращение копирования больших DataFrame через `copy()` без необходимости.

### 5.2. Спецификация вывода Агента-Роутера по промпту

### 5.3. Гетерогенное ранжирование и Blending
* При формировании портфеля объединяются алгоритмы из разных математических парадигм:
  * Градиентный бустинг на симметричных oblivious-деревьях (CatBoost);
  * Градиентный бустинг на асимметричных depth-wise деревьях (HistGB / LightGBM);
  * Рандомизированный бэггинг (ExtraTrees / RandomForest);
  * Линейные регуляризованные модели (Ridge).
* Оптимизация весов ансамбля (Blending) проводится на Out-of-Fold (OOF) предсказаниях. Веса должны допускать значение `0.0`, чтобы слабые модели автоматически исключались и не портили результат.

## 6. ИТОГОВЫЕ ТРЕБОВАНИЯ К АВТОНОМНОЙ СИСТЕМЕ

Создаваемая система обязана быть:
1. **Отказоустойчивой (Bulletproof)**: генерировать валидный сабмит на первой минуте (Fail-Safe защита), никогда не падать с `Exit Code != 0`, корректно перехватывать ошибки LLM и песочницы кода.
2. **Самокорректирующейся (Self-Correcting)**: использовать замечания Критика для изменения направления генерации признаков, автоматически делать Rollback при ухудшении метрики и останавливать бесполезные вычисления (Early Stopping).
3. **Экономной по времени и ресурсам**: укладываться в рамки 8 CPU / 32 GB RAM / 3 часа, бережно расходовать токены Qwen3.8-27B.
4. **Универсальной**: выдавать конкурентный результат на незнакомых скрытых задачах благодаря системному подходу к данным, валидации и портфелю моделей.
